# Datavyx 账户关闭与保留流程运行手册

2026-11-26。责任主体Datavyx, LLC；处理入口support@datavyx.com（独立Google Workspace邮箱）。本手册与已确认期限配套；具体启用时间、运行commit、备份回执和计时器状态以发布记录为准。没有生产验证记录时，不把源码或本手册视为已启用。

## 1. 期限与范围

- 账号存续期间保存正常知识、来源、更正历史和可恢复删除。普通删除立即退出正常读取/统计，不在30天后自动永久清除。
- 收到关闭邮件后核验账户控制权、可信issuer/sub及实际空间成员。以核验完成时间固定30天活动数据截止和60天备份截止；重试不重新计时。
- 新旧token、换客户端和重新登录均受签名关闭屏障限制。外部关闭记录、专用key与历史purge ledger独立于图谱/数据库备份，不得随数据库回滚。
- 活动数据流程涵盖正式与候选中的个人空间及身份绑定；共享空间只去除关闭账号成员，保留其他人内容。唯一拥有者的旧空间必须明确分类，共享拥有者需有另一拥有者；不猜测，不整库清空。
- Auth0账号/客户端授权与历史语义副本由明确账号范围的人工运营步骤核对并记录实际处理凭据；不通过公开MCP或伪造purge工具执行。未完成的外部任务进入持久队列，超过30天daily失败报警，不能报结案。
- 备份最长30天轮转；技术/安全日志最多30天；必要支持邮件/工单结案后12个日历月。闰年2月29日到下一年2月28日，不按365天粗算。

## 2. 支持邮箱与身份核验

独立support邮箱管理员负责处理，不使用当前ken连接擅自读取/清理support邮件。不要索取Client Secret、密码、API Key、访问令牌或完整聊天历史。

1. 在support邮箱建立专用工单标签：Datavyx/Open、Datavyx/Closed、Datavyx/LegalHold。只对必要支持往来标记，不整箱归类或清空。工单编号不能包含邮件正文或敏感身份字段。
2. 通过已认证Datavyx身份与支持邮箱核对账户控制权；不能只按相同显示名或一封未经核验的邮件确定目标。可信actor为后端由issuer/sub派生的64位十六进制摘要，不是邮箱，不由调用Agent自由指定。
3. 明确是普通可恢复删除还是账户关闭。前者使用正常11工具；后者由受保护管理主机处理。记录核验时间、账号范围、共享成员、个人空间分类及后续处理状态。不创建产品确认卡。
4. 登记关闭case并先block；管理命令输出只有状态、计数和期限。未经核验不得调用block/erase；本手册不是批量关闭用户的授权。

## 3. 受保护账户管理

代码入口knowledge-management-demo/scripts/mcp_retention.py。只接受root、正式/候选固定URI、签名/校验通过的不可变运行包，以及ATLASAI_RETENTION_AUTHORIZED_COMMIT精确commit。加载受保护MCP env，不使用shell展开、不继承模型密钥；通过现有run_env.read_env或EnvironmentFile执行。

动作：

- block --actor ACTOR --verified-case CASE：先持久保存签名身份屏障，再按真实owner/member确定范围并停用成员。唯一旧空间仅在确有个人归属证据时加--legacy-personal EXACT_WORKSPACE。
- erase --actor ACTOR：事务清理已核验个人数据、原文、历史、旧回执和成员。保留最小伪匿名防复活标记；跨空间依赖/范围变化会整体拒绝，不能部分删完后报成功。
- reconcile：对已有签名关闭请求补处理当前正式/候选副本。数据库提交后完成签名中断可幂等重试；旧库恢复后先重放关闭约束再开放服务。
- provider-complete --actor ACTOR --provider auth0|legacy_copies --provider-receipt ACTUAL_REFERENCE：仅在实际处理/核对完成后登记，不把占位文字当回执。状态文件只保留回执摘要。

Auth0步骤由具备管理权限的人执行：撤销该Datavyx账号相应客户端授权/刷新会话，核对该身份是否仅属于Datavyx；若是，按核验范围处理其身份资料；若同一身份服务另有独立产品用途，不误删其他产品账号，记录用途和分离处理依据。此前浏览器Auth0访问未获许可，不能换接口绕过。Datavyx后端屏障在提供方操作前已阻断既有token，不能将提供方操作未完成误报为整个账户清理完成。

legacy_copies步骤核对旧语义库、导出物、管理副本和其他实际个人数据位置；无匹配数据也须有盘点结果。旧Graphiti/API保持停用，不为清理重启。此项不能用自动删除整个旧库替代账号范围校验。

## 4. 备份、轮转和恢复

新备份固定根目录/home/ubuntu/atlasai-deploy/backups/retention，仅登记直接常规文件；签名清单在/var/lib/atlasai-mcp/account-state/retention.json。密钥和屏障不能放进数据库图谱备份，也不能在恢复时用旧副本覆盖当前屏障。

1. 正式/候选一致逻辑备份先取元数据锁，再按排序锁全部数据集。自动建空间和关闭事务共享元数据锁，写入事务共享数据集锁。快照包含所有节点/关系及属性，不仅旧label白名单。数值、纳秒时区时间、日期、duration、坐标点和二进制保留类型，不转成不可恢复说明文本。
2. 旧语义副本仅在旧API停止情况下做只读一致捕获；该副本不重新接入知识查询、不启动Graphiti。新文件以legacy-semantic profile登记。
3. 每个备份恢复到专用临时Neo4j，端口仅127.0.0.1:17696。只使用现有neo4j:5.26-community镜像，不拉新镜像，不挂载生产卷；/data和/logs为tmpfs。恢复前库必须为空，恢复后逐图谱fingerprint核对，最后仅删除带本次随机所有权label的临时容器。正式17693、候选17694和旧语义17695都不是恢复覆盖目标。
4. 哈希/范围/新鲜度及真实还原证明都通过才轮转；每个profile必须有自己的36小时内有效后继，不能用候选备份替代正式备份。到期前只读计划，过期后按清单删除。
5. 历史四组目录只能按固定白名单逐组登记，所有后继profile（正式、候选、旧语义）验证后才到期处置。时间按整个目录最新mtime保守计算，不把旧源文件日期当作新备份完成时间。目录中有链接/特殊文件/变更会拒绝。首次仅10月26日组按实际盘点可能已到期；实际范围以签名计划为准。
6. 文件unlink后中断可根据持久intent重试；历史目录递归删除一半后中断会拒绝自动扩大清理，要求核对受保护原清单。任何缺失、篡改、无有效后继都返回错误并保留其余副本。
7. 恢复前停止写入，保持外部签名状态和独立key；用兼容data_contract=3/account_closure=1的运行包恢复。先核验旧purge ledger，再执行关闭reconcile和readiness检查，最后才能服务。新版本拒绝退到不认识关闭屏障的v2运行包。不能为了健康检查通过而重置key、删除关闭文件或绕过屏障。

本机备份不能应对整台主机丢失；尚未配置独立异地存储，不把本地轮转冒充异地灾备。若将来增加异地/人工下载副本，必须先加入相同到期清单、权限和恢复门槛，不能无限保留。

## 5. 定时任务和日志

atlasai-mcp-retention.timer每天UTC02:20附近执行，Persistent补跑；正式、候选和旧语义备份均真实恢复核对后轮转。任务失败在systemd返回非零，责任管理员每日查看最近一次结果和待处理case，不能仅查看timer存在。

新MCP正式/候选及retention服务使用LogNamespace=atlasai-mcp；journald配置Storage=persistent、MaxRetentionSec=30day、MaxFileSec=1day、ForwardToSyslog=no。日志仅计数/状态/安全错误字段，不记录原文、完整参数、邮件正文或凭据。安装新的namespace规则前后分别验证真实写入归属和最旧记录，旧全局journal/rsyslog中的MCP历史记录单独盘点，不能仅配置namespace就声称历史副本已到期清理。

nginx规则替换现有/etc/logrotate.d/nginx，不能另装同路径重复规则；沿用daily、权限/日志重开机制，设置rotate30/maxage30，并核对安静日志的到期实际处理。不要对整个/var/log盲删，不关闭安全日志或改写业务源数据。

实际启用后检查：systemctl list-timers --all；systemctl status atlasai-mcp-retention.service；journalctl --namespace=atlasai-mcp -u atlasai-mcp-retention.service；nginx -t；logrotate -d；各服务readiness；最新有效备份及旧副本签名到期计划。失败和逾期必须记录到运行报告。

## 6. 支持工单12个月流程

1. 真正结案时才登记ticket-close：case引用、明确Gmail message_id列表、实际closed_at（UTC时间戳）。没有关闭时间、仍打开、范围未核验的邮件不得入到期清单。新增往来重开case时不能沿用已结案截止，需要管理员重新核验记录。
2. ticket-due仅生成到期工单队列，不读取邮件内容、不扫邮箱。服务器不能访问独立support邮箱，因此到期邮件实际处理当前由support管理员执行，不伪称自动Gmail删除已接通。
3. 管理员使用原case和明确消息ID核对所有必要往来、附件、下载副本和保全情况。仅处置已到期且无具体有效保全依据的那个case。保全必须单独登记理由、责任人、受限位置和解除条件，不能不填期限地无限延长所有工单。
4. Gmail的“移到垃圾箱”通常还存在保留期，不足以证明已不可读；不得调用清空整个垃圾箱。管理员对本case的明确消息完成最终到期处置并核对消息不再可读取，再记录实际提供方操作引用。
5. ticket-complete只有到期case可登记；完成后移除消息ID和旧case关闭细节，只保留最小处理回执摘要。未取得真实提供方回执不登记完成。剩余到期工单让daily返回失败，供责任管理员跟进。
