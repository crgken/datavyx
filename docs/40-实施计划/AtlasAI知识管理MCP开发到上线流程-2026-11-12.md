## 1. 固定顺序与授权边界

```text
明确流程与范围
  → 用户明确开始开发
  → 当前目录创建开发分支并建立 Git 跟踪边界
  → 本地实现和隔离数据库验证
  → 提交并推送候选代码，生成可追溯候选包
  → 服务器测试入口 + 隔离数据兼容演练
  → 真实 ChatGPT 闭环验收
  → 提交可审阅发布报告，取得正式发布指令
  → 合并并推送 main，核对唯一发布版本
  → 正式窗口备份、迁移、停旧与切换
  → 上线验收及发布记录
```

产品内不需要人工确认，不等于开发和生产发布自动获得授权。本次“明确流程”只授权整理流程文档；用户明确“开始开发”等指令后才修改实现代码。开发授权覆盖本地实现、隔离测试及必要的受保护测试部署，不自动包含正式数据库迁移、停旧系统或生产入口切换。

只有全部测试及演练完成、具体发布报告可供审阅之后，才把“正式发布”作为最后的用户决策。此前已获得的明确授权不重复询问。范围变更或需要新的账号配置时，只提出缺失事项，不反复确认常规技术步骤。

## 4. 本地开发顺序

1. 定义并校验严格输入/输出契约及图谱目录/局部上下文协议，先固定字段、来源、身份、冲突和幂等规则。
2. 建立不导入旧 Agent/Graphiti/审批链的 Neo4j repository，先实现账号空间、目录、候选、详情、来源和精确查询。
3. 实现新增直写、source_only、来源支持、冲突资格、事务回滚、幂等及 `get_receipt`。
4. 注册 MCP 工具及真实读写标注，完成 OAuth、错误转换、限额、分页、审计及最小运行配置。
5. 增加幂等迁移、检查和回滚说明；将原文、原 ID、历史状态与未执行提案分开核对。
6. 实现新的 MCP 启动/发布/健康检查入口，验证依赖白名单、旧接口关闭方式和无模型网络请求。

每个阶段做必要验证；失败修复后只重跑受影响测试并完成最终规定验收，不在未改动和无新疑点时反复重做全部测试或打包。

继续采用已使用的“Git 提交 → 推送 → 合并 main → SSH 上传 → 服务端应用发布 → 验证”方法。MCP 专用发布入口只处理已提交的 MCP 代码、独立依赖锁、迁移/校验和服务配置，不安装旧模型依赖、不触发旧 API、不重新处理网页资产。

传输候选包是把已提交源码和必要部署文件压缩上传；它不是 Flutter 构建、前端重建或新建容器镜像的同义词。候选包建立校验值后复用同一包演练和发布；版本、依赖或必须纳入的配置模板改变才生成新候选。

服务端使用独立 MCP 虚拟环境与启动单元，避免复用含旧模型包的 Python 环境后误报依赖已移除。运行密钥保持服务器管理，不进入 Git、候选包或回显日志。

## 6. 候选部署、数据演练与 ChatGPT 验收

### 候选版本

- 本地测试通过后，将代码和必要部署说明提交并推送到开发分支，工作区改动与候选包边界清楚。
- 从明确提交生成候选包，记录完整 commit、文件清单、依赖锁与包 SHA-256。不能把未提交文件混入后称为 Git 发布。
- 服务器以独立测试配置、进程和数据库运行候选；测试路由不能覆盖正式 `/mcp`、旧网页、旧 API 或业务配置。
- 测试端点必须有访问限制且能被目标 ChatGPT 账号按实际认证方式使用。公开到互联网不等于允许匿名访问。

### 数据演练

- 从已授权的、具有一致性的生产数据备份建立隔离副本；不把真实数据原文放入 Git 或普通日志。使用已有一致性备份时先评估时效和版本，不能只复制正在运行的数据库卷。
- 如果获取新的一致性备份需要停库，必须另行安排已授权窗口；演练不能擅自停止在线数据库。没有安全副本时先完成合成数据验证，并将真实数据演练明确列为未通过项。
- 若采用无需停库的逻辑验证副本，必须先验证它使用旧写入链相同的版本节点锁和成员/空间保护、有限事务时长、始终回滚及源属性保持；记录快照时点和实际锁定时长。不能把普通非一致性扫描或逻辑验证副本当作最终离线卷恢复备份。
- 在副本执行迁移、核对、重放及恢复，检查原 ID、来源、数量、关系、精确数值和旧草稿排除规则。
- 候选不得写正式库，旧线上服务不因演练停止。真实数据迁移与合成工具流程分别出报告。

### ChatGPT 实测

必须在候选对应的测试入口完成：认证 → 目录 → 候选/局部关系 → Agent 结构化录入 → 查询 → 来源 → 原请求重试/回执核对。

同时检查删除/修改请求不触发写操作、无产品内批准步骤、跨空间访问被拒绝，以及不配置模型 key、阻止模型端点网络后流程仍成立。MCP Inspector、单元测试和服务器 200 响应不能代替真实 ChatGPT 闭环。

## 7. 正式发布前提交给用户的报告

正式发布请求必须对应具体候选，至少提供：

1. 版本：分支提交、依赖锁、候选包与校验值，以及预计合并到 main 的内容。
2. 验证：本地/真实 Neo4j、服务器副本演练、真实 ChatGPT 的通过结果和明确未覆盖项。
3. 数据：迁移差异、是否需要 schema 变化、备份位置和已验证恢复方式，不显示数据原文或凭据。
4. 切换：会关闭哪些旧接口与 worker、网页如何处理、认证与路由如何指向新 MCP。
5. 维护：根据演练说明停写/必要停机范围与预计时长；没有实测依据不编造时间。
6. 回滚：开放写入前和开放写入后的不同处理方式，如何避免丢失新记录。

用户明确正式发布后，再合并/推送 main 并执行生产动作。若用户已经明确授权该具体发布，不再重复请求相同授权。

## 8. Git 发布顺序与候选一致性

```text
codex/mcp-neo4j
  → 提交并推送开发分支
  → 候选测试与迁移/客户端演练通过
  → 审阅最终 diff 和发布报告
  → 正式发布授权
  → 同步 origin/main，合并开发分支
  → 推送 main
  → 核对服务器待部署提交与 origin/main 一致
  → 应用已验证候选
```

优先 fast-forward，使已测提交直接成为 main。若 main 有新改动、发生冲突或合并结果改变运行内容，应重新验证受影响项并重新锁定候选；不得部署未经验证的合并结果。只增加不影响运行的说明文件也必须保持发布清单清楚，不能把两个不同包冒称同一包。

未经 Git 提交/推送的临时线上修改不作为正式修复。紧急情况也必须保留差异、验证和最终回写版本的记录，不能长期以服务器漂移代替仓库版本。

## 9. 正式维护窗口的执行次序

1. **发布前检查**：确认用户发布指令、main 提交、候选包、可用空间、配置、认证、已验证迁移及恢复材料；失败则不进入维护。
2. **进入写入屏障**：暂停旧入口新写入，等待在途请求完成或明确中止并保存状态；旧 Graphiti worker 停止生成新投影，禁止新旧系统并发写同一数据范围。
3. **最终一致性备份**：保存规范数据、必要旧语义数据、代码/配置及版本。只有既定备份方式需要时才短暂停库，完成后恢复数据库；不能在没有备份与恢复路径时继续。
4. **应用发布与迁移**：部署已验证 MCP 代码和依赖，执行已演练的版本化迁移。没有 schema 变化时不重复迁移或重建数据库。
5. **先限制开放**：MCP 对维护/验证账号开放，普通用户尚不写入；核对登录、权限、规范数据和来源，跑专用合成数据的最小闭环。合成写入不混入真实用户空间，保留测试标识。
6. **停旧与切入口**：新 MCP 接管正式 `/mcp`；停用旧自然语言/语音/修改/确认 API 和旧模型/Graphiti worker。旧网页按已公布方案显示静态迁移说明，不构建 Flutter。
7. **开放新写入**：所有关键检查通过后解除新服务写入限制，允许正式账号仅新增和查询。
8. **上线核对**：再次核对真实客户端、版本、服务日志、授权及后台任务，确认无后端模型调用；写入记录必须能查询和追溯。

维护期间出现失败，应保留实际执行阶段和错误；不能把写入屏障解除当作修复，也不能先重启所有数据库碰运气。只有失败原因确需时才进行相应的服务操作。

## 10. 健康、验收与回滚判定

上线不能只以旧 `/api/mobile/session` 返回 401 为成功。新的检查至少覆盖：

- 新 MCP 进程、Neo4j 连接和必要约束/索引正常。
- 未认证访问正确拒绝；OAuth 发现与真实登录可用，受保护数据不会匿名返回。
- 实际 MCP 协议请求成功，工具清单/版本与候选一致，没有旧确认、修改或任意 Cypher 工具。
- 合法记录返回已提交回执，查询/来源可取回，同请求重试不新增第二份。
- 旧写入与后台模型任务确实停用；未访问 Graphiti 或第二语义库。
- 安装模块、依赖锁、服务配置模板和提交/包校验值与测试候选一致；静态资源没有因本次发布被重新构建。

开放新写入前失败：按演练恢复旧服务和必要数据，明确记录旧模型重新启用属于回滚，而非新 MCP 的隐式降级。

开放新写入后失败：先保护新记录和回执，优先前向修复或兼容新数据的代码回滚。旧版本若不能安全读取新数据，不直接切回；禁止恢复旧卷覆盖新增记录。

旧 Graphiti 数据、第二 Neo4j 容器与卷的永久删除，不包含在首轮上线动作里；封存并证明无依赖后，再作为独立清理事项处理。

## 11. 上线完成的定义

发布记录应写明实际提交、包校验值、迁移版本、服务切换、真实验收、备份/恢复位置和剩余问题，并更新[线上功能说明](../60-子系统与工具说明/Datavyx线上功能与业务流程说明-2026-11-11.md)、[当前基线](../10-当前基线/项目当前基线-2026-11-11.md)及开发说明。

只有完成生产切换与上线验收，才把文档状态改成“已上线”。已写好方案、单元测试通过、候选服务启动或 main 已推送都不能单独等同于上线完成。

本轮仅确定流程，不创建分支、不改忽略规则或发布脚本、不安装依赖、不构建、不停服务、不执行迁移。
